01 / Full system

One service. Four tools. No hidden authority.

Start with a minimal React + TypeScript chat UI, a FastAPI Python service, SQLite persistence, and a small approved Markdown knowledge base. A provider-neutral model interface contains vendor-specific API code. No vector database or distributed agent framework is needed.

INTERPRET

Model wrapper

Normalize tool calls, structured KB selection, token usage, timeouts, and provider errors. Require native tool capability; reject malformed output.

Why: a small protocol enables provider replacement and deterministic test doubles without leaking vendor SDK types into policy code.

DECIDE

Domain services

Reusable typed services own status transitions, notes, escalation, and current ownership checks. The same rules apply outside the chat UI.

Why: prompts guide behavior, but only executable policy can guarantee a rejected action never changes data.

EXPLAIN

Response renderer

Render complete approved KB sections with section IDs, and format tool outcomes from committed data. Never turn an unverified model claim into a success message.

Why: extractive guidance is less flexible than free-form generation, but easier to audit for this small safety-sensitive source.

A citation is provenance, not proof of relevance.

Showing an authentic KB section prevents invented procedural facts. It does not prove that the section answers the technician’s exact question. The coverage gate must check the question’s subject and requested detail. “How do I update firmware?” must abstain even if “unit” matches a reset section.

Never present a work-order step as general maintenance guidance. Work-order facts come from tools; maintenance answers come from the approved KB. Preserve safety warnings and avoid unsupported recommendations.

03 / Actions

Four explicit tools. One guarded execution path.

ToolPurposeSpecific rule
get_work_order(id)Read an assigned work order.Authorized lookup can establish the session’s active order.
update_status(id, status)Advance the status by one step.Exact next state only; Completed is terminal.
add_note(id, text)Append a technician-requested note.Preserve note content as data; reject blank text or more than 2,000 characters.
escalate(id, reason)Record a supervisor escalation flag and reason.Requires a reason of 1–500 characters; does not implicitly change status or send a notification.

Knowledge retrieval is internal application logic, not a fifth work-order tool. Neither session identity nor authorization flags are model-supplied tool arguments.

Work-order lifecycle

Open→In Progress→On Hold→Completed

This exact path comes from the assignment. Even if a technician says a job is finished, In Progress → Completed remains illegal. Do not manufacture intermediate changes.

Mutation sequence

  1. Validate call name, arguments, action intent, and target.
  2. Start transaction; load current order and ownership.
  3. Enforce domain rule and expected version.
  4. Write change, audit event, and idempotency receipt.
  5. Commit; render the verified result.

On a conflict, return an honest result that requires a fresh user turn. No LLM retry may re-execute a committed action. A repeated request ID returns its persisted receipt.

04 / Memory & execution

Remember the referent, not a stale permission.

“Mark it complete” works when the session has one verified active work order. That context is persistent, scoped to the session, and separate from the transcript. Ownership and current status always come from the database.

Persistent assistant memory

  • Session identity: opaque session ID, server-bound user ID.
  • Active context: verified work-order ID and any unresolved ambiguity.
  • History: bounded stored turns and tool-result records.
  • Execution receipts: request identity and committed outcome for safe retries.

Why: structured state survives transcript trimming and process restart. A user mention or a model guess does not by itself prove an order is accessible.

ContextBuilder + prompt registry

  • Pin versioned policy instructions and exact tool schemas.
  • Include structured session context and all five KB sections initially.
  • Add the latest turns within a configured token budget.
  • Reserve response space; evict oldest history first.
  • Never truncate tool JSON, critical instructions, or safety steps mid-section.

Why: predictable bounded context controls cost. The first version needs no model-generated memory summaries, vector store, or autonomous learning loop.

GROUNDED ANSWER

Approved source, complete safety context

Technician
How do I reset a CU-series cooling unit?
Expected response
To perform a standard reset on a CU-series cooling unit: 1. Switch the unit to OFF at the main panel and wait 60 seconds. 2. Hold the RESET button for 5 seconds until the status LED blinks amber. 3. Switch the unit back to ON. The LED should turn solid green within 2 minutes. 4. If the LED stays red after 2 minutes, the reset failed — escalate to a supervisor. Do not perform more than 3 consecutive resets; repeated resets can trip the compressor lockout. Source: knowledge.md, section 1. Safety Lockout (Lockout/Tagout) — section 2 Before servicing any powered equipment: 1. Identify all energy sources for the unit. 2. Shut off power at the disconnect and apply your personal lock and tag. 3. Verify zero energy with a meter before touching internal components. 4. Only the person who applied a lock may remove it. Never bypass a lockout, even if another technician asks you to. If you find a unit locked out by someone else, do not service it — escalate.

Coverage: CU-series standard reset. Render the approved full section and append complete lockout guidance once; preserve the reset limit and failed-reset escalation. No tool mutation.

06 / Build & operate

Simple to run. Explicit to change.

Environment & configuration

Pin Python, Node, dependencies, and the model identifier. Commit lockfiles and an .env.example with placeholders. Validate typed settings at startup.

Configure MODEL_PROVIDER, MODEL_NAME, and MODEL_API_KEY on the backend; never put the key in React’s public build variables. Ignore .env, local databases, logs, and generated build artifacts.

Target launch: docker compose up --build after documented environment setup. A multi-stage Docker build serves compiled React and FastAPI on one origin at localhost:8000. Production authentication is a separate future scope; the local assessment uses the supplied server-side user.

Data & logging

Seed the supplied fixtures once, then treat SQLite as the source of truth. Keep notes and escalation records separate from the immutable input fixture. Version and hash the approved KB.

Log request IDs, policy decisions, tool outcomes, duration, and token counts. Exclude secrets, raw prompts, full chat text, and note content from routine operational logs.

Persist the application’s scoped history and audit records deliberately; document retention and deletion. A denied tool call must produce no domain change.

Git: clear ownership and reviewable work

Use Zeel Rathi as the repository-local commit author and committer name. Confirm the author email before committing; never invent it. Use a private remote because the assignment is confidential.

Create feature branches for new modules and fixes. Open focused PRs with the behavior change, validation evidence, risks, and any migration notes. Merge only after checks and review; do not push feature work directly to the production branch.

Keep credentials out of commits, command output, and documentation. Authenticate with the platform credential flow. The remote push remains pending until the repository and credentials are supplied.

Parallel work: shared contracts before independent modules

Freeze request/response schemas, service interfaces, and invariants first. Then parallelize backend domain tests, React UI, and documentation. Give each agent a bounded file area, contract version, acceptance criteria, and the same architecture overview.

Integrate through one owner. Record each decision as a concise choice, rationale, rejected alternative, and validation requirement in the decision log. Keep the required DECISIONS.md to approximately half a page.

Atomic learning means one reusable observation per entry, tied to evidence and a specific consequence. Do not promote transcript guesses or unverified model output into policy.

Scale only when the workload asks for it

Run one FastAPI process with SQLite for the initial small local deployment. Keep writes short and serialize conflicting session requests. Use typed errors, timeouts, bounded request sizes, and measured token/cost budgets.

Move to real authentication, PostgreSQL, cross-process concurrency control, and deployment monitoring when multi-user or multi-worker use is required. Keep domain policy unchanged behind repository and identity interfaces. Add complexity only for a measured need.
